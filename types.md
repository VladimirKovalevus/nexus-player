# Анализ типов данных и их взаимодействия

Этот документ описывает поток данных в приложении, начиная от уровня базы данных, через доменные модели и до объектов передачи данных (DTO), используемых для фронтенда.

## Архитектура потока данных

Данные в приложении проходят через три основных уровня:

1.  **Сущности базы данных (Entities):** Находятся в `nexus-player-backend/src/library/entities_v2/`. Это плоские структуры, которые напрямую соответствуют таблицам в базе данных. Сложные данные (например, `TrackSource`) хранятся в виде сериализованных JSON-строк.
2.  **Доменные модели (Domain Models):** Находятся в `nexus-player-backend/src/library/models.rs`. Это более богатые, структурированные представления данных, использующие вложенные структуры и перечисления (enums). Они представляют основную бизнес-логику приложения. Преобразование из сущностей в доменные модели происходит в `nexus-player-backend/src/library/convert_v2.rs`.
3.  **Объекты передачи данных (DTOs):** Находятся в `nexus-player-frontend/src-tauri/src/dto.rs`. Это упрощенные, плоские структуры, предназначенные для отправки на фронтенд. Они содержат только те поля, которые необходимы для отображения в пользовательском интерфейсе.

## Поток данных для `Track`

1.  **`entities_v2::track::Model` (Сущность БД):**
    *   Плоская структура с базовыми типами (`String`, `Option<String>`, `i64` и т.д.).
    *   Содержит множество метаданных: `description`, `album_artist`, `year`, `genre`, `track_number`, `file_format`, `sample_rate`, `channels`, `bitrate` и другие.
    *   `source_data` и `cache_data` хранятся в виде JSON-строк.

2.  **`models::Track` (Доменная модель):**
    *   Богатая структура, которая десериализует JSON-строки в полноценные типы, такие как `TrackSource` и `CacheStatus`.
    *   Группирует связанные поля во вложенные структуры, например `Metadata` и `AudioInfo`.
    *   Использует более строгие и выразительные типы (`TrackId`, `DateTime<Utc>`).

3.  **`TrackDto` (DTO для фронтенда):**
    *   Значительно упрощенная версия, содержащая только необходимые для отображения поля.
    *   **Поля, которые отбрасываются при конвертации:**
        *   `metadata.description`
        *   `album_artist`
        *   `year`
        *   `genre`
        *   `track_number`
        *   `cache` (статус кеширования)
        *   `audio_info` (sample_rate, channels, bitrate)
        *   `last_played`
        *   `added_at`
        *   `updated_at`

## Поток данных для `Playlist`

1.  **`entities_v2::playlist::Model` (Сущность БД):**
    *   Простая структура, содержащая `id`, `title`, `description`, `creator` и временные метки.
    *   Треки не хранятся напрямую, а связываются через соединительную таблицу `playlist_track`.

2.  **`models::Playlist` / `models::PlaylistWithTracks` (Доменные модели):**
    *   `Playlist` — это структурированная версия сущности.
    *   `PlaylistWithTracks` объединяет `Playlist` и `Vec<PlaylistTrack>`, где `PlaylistTrack` содержит только `track_id` и `position`, **но не полную информацию о треке**.

3.  **`PlaylistDto` / `PlaylistWithTracksDto` (DTO для фронтенда):**
    *   `PlaylistDto` — это упрощенная версия плейлиста с добавленным полем `track_count`.
    *   `PlaylistWithTracksDto` предназначена для хранения `PlaylistDto` и **полного списка треков** (`Vec<TrackDto>`).

## Ключевые выводы и рекомендации по оптимизации

### 1. Производительность: Критическая проблема N+1 запросов

*   **Проблема:** При загрузке плейлиста с треками (`get_playlist_with_tracks`) выполняется `N+2` запросов к базе данных, где `N` — количество треков в плейлисте. Это крайне неэффективно.
*   **Расположение:** Проблема находится в `nexus-player-frontend/src-tauri/src/commands.rs`, в функции `get_playlist_with_tracks`. Код итерируется по списку ID треков и для каждого ID выполняет отдельный запрос к БД.
*   **Рекомендация:**
    1.  Создать в репозитории (`playlist_repo.rs`) новый метод, который будет использовать `JOIN` для загрузки плейлиста и всех связанных с ним треков за **один запрос**.
    2.  Создать новую доменную модель, например `PlaylistWithFullTracks`, которая будет содержать `Playlist` и `Vec<models::Track>`.
    3.  Обновить команду `get_playlist_with_tracks`, чтобы она использовала новый эффективный метод, устранив цикл.

### 2. Качество кода: Сломанная и обходимая конвертация в DTO

*   **Проблема:** Реализация `From<models::PlaylistWithTracks> for PlaylistWithTracksDto` в `dto.rs` некорректна (она всегда возвращает пустой список треков) и обходится ручным созданием DTO в `commands.rs`.
*   **Рекомендация:** После исправления проблемы N+1, создать корректную реализацию `From` для новой доменной модели (`PlaylistWithFullTracks`), чтобы централизовать и упростить логику конвертации.

### 3. Избыточность данных: Неиспользуемые метаданные трека

*   **Проблема:** Множество полей (`year`, `genre`, `track_number` и т.д.) загружаются из БД, но отбрасываются при создании `TrackDto` и не доходят до фронтенда.
*   **Рекомендация:** В настоящее время это является хорошей оптимизацией, так как уменьшает объем данных, передаваемых на фронтенд. Однако, стоит пересмотреть требования к UI. Если эти поля нужны для отображения или фильтрации, их следует добавить в `TrackDto`.

### 4. Консистентность данных: Временные метки и обложки

*   **Проблема:** Временные метки обрабатываются inconsistently: `DateTime<Utc>` в моделях и `i64` (unix timestamp) в DTO. Поле `artwork_url` в `TrackDto` всегда `None` при загрузке списков, что говорит о ленивой загрузке.
*   **Рекомендация:**
    *   **Временные метки:** Стандартизировать формат для всех DTO, например, используя строки ISO 8601, которые легко парсятся в JavaScript.
    *   **Обложки:** Текущий подход с ленивой загрузкой является приемлемым для производительности.

## Создание плейлиста с внешними треками (`TrackSource::External`)

Для создания плейлиста с треками, которые не хранятся локально, в `LibraryService` существует функция `create_playlist_with_tracks`. Она принимает `runtime_playlist` и пытается сохранить каждый трек из него в библиотеку.

Эта функция полагается на конвертацию из `audio::Track` в `models::Track` через вызов `.into()`. Однако, точная реализация этого `From` трейта не была найдена в ходе автоматического анализа, что является аномалией, так как проект компилируется.

**Что это значит:**

Чтобы создать плейлист с внешними треками, необходимо:
1.  Собрать объект `crate::playlist::playlist::Playlist` на бэкенде, заполнив его треками (`audio::Track`), у которых `source` будет `TrackSource::External { system: "...", id: "..." }`.
2.  Передать этот объект в функцию `library_service.create_playlist_with_tracks(...)`.

Эта функция должна взять на себя логику по сохранению информации об этих внешних треках в базу данных и созданию плейлиста, связывающего их. Механизм, обеспечивающий эту конвертацию, требует дальнейшего, более глубокого ручного исследования кода.
